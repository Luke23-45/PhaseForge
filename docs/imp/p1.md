## Important methodological risks

### 1. The object-state input is privileged information

The model receives exact world-frame object poses. This is acceptable for an architecture sanity check, but it is effectively an oracle state channel.

You should explicitly describe the results as:

> A state-oracle architecture evaluation of phase-conditioned MoE routing.

Do not compare these results directly with vision-based LIBERO leaderboard methods.

### 2. Report seen-task and held-out-task performance separately

Your training split is task-level: approximately 81 tasks for training and 9 for validation. However, rollout evaluation uses all 90 tasks.

Therefore, `libero_90` is not uniformly “seen during training.” Report at least:

- Training-task performance.
- Held-out-task performance.
- Overall performance.

Otherwise, an aggregate score may hide poor generalization.

### 3. The router initialization is only a weak phase signal

In [phase_moe.py](C:\Users\Hellx\Documents\Programming\python\Project\Neryva\PhaseForge\phaseforge\models\phase_moe.py), router weights are initialized from normalized latent centroids, but the latent vectors themselves are not normalized during routing.

The resulting dot product is not strictly a cosine similarity. This may make the intended phase-based initialization less meaningful than expected.

You should measure immediately after bootstrapping:

- Phase-to-expert NMI.
- Routing entropy.
- Per-expert usage.
- Action loss before and after Stage 2 initialization.

### 4. Your balancing metric and balancing loss are not perfectly aligned

The loss balances top-1 routing, while the utilization metric counts all top-k assignments. Since your router uses top-2 routing, the reported balance score and optimized balance objective measure slightly different things.

This is not necessarily a fatal bug, but it should be documented or corrected before making strong claims about expert balance.

### 5. Phase labels are heuristic

The phase labels are generated by rules based on robot motion and gripper state. That is reasonable for bootstrapping, but they are not ground-truth semantic labels.

You should describe them as:

> Rule-based pseudo-labels representing approximate manipulation phases.

You should also manually inspect labels from several tasks before training.

## What you should do next

Do not begin the full 8-model × 3-seed experiment immediately.

Use this staged validation sequence:

### Gate 1: Real-data ingestion

Run the object-index census and verify:

- All 90 LIBERO tasks are indexed.
- Every task’s state dimensions are valid.
- No object exceeds the 16-slot capacity.
- Quaternion values are normalized.
- Decoded object poses are finite.

Then run the existing correctness script:

```powershell
uv run python scripts/verify_correctness.py
```

### Gate 2: Train/evaluation parity

For several real tasks and episodes:

1. Decode object state from HDF5.
2. Reset MuJoCo to the same state.
3. Extract object observations from the environment.
4. Compare the two vectors numerically.

The difference should be close to floating-point tolerance. This is the most important technical gate.

### Gate 3: Small smoke experiment

Train only these three models first:

- `bc`
- `warmstart_moe`
- `phaseforge`

Use:

- 3–5 tasks.
- 5–10 episodes per task.
- 1 seed.
- Shorter training schedules.

The goal is only to confirm that rollout success becomes nonzero and that the object-state channel is actually useful.

### Gate 4: Main experiment

Only after the smoke experiment succeeds, run the full comparison:

- BC.
- Scratch MoE.
- WarmStart MoE.
- PhaseForge.
- Teacher-forced model.
- Random-router ablations.
- Oracle model, clearly marked non-deployable.

Your primary comparison should be:

> `phaseforge` versus `warmstart_moe`

That is the cleanest test of whether phase bootstrapping adds value beyond ordinary BC pretraining.

## How to interpret possible outcomes

| Result | Interpretation |
|---|---|
| BC and MoE models all remain near 0% | Object-state parity, action control, or environment setup is still broken |
| BC succeeds but MoE does not | MoE training/routing is harming the policy |
| MoE succeeds but NMI is near 0 | MoE may help through capacity, but not through phase specialization |
| PhaseForge beats WarmStart consistently | Evidence supporting the hypothesis |
| PhaseForge matches WarmStart | Phase bootstrapping may not provide useful benefit |
| PhaseForge is worse than WarmStart | Evidence against the current bootstrapping method |
